#### Question: Open
id:: 48739742-ff8b-4d08-8649-8ca94563965a
content::
A lab's untrusted agent edits the configuration of the lab's services in response to engineers' tickets, for example raising the web server's connection limit, changing the database's backup schedule, or adjusting the retry and quota settings of Kestrel, the lab's in-house job scheduler. A small trusted model reviews every change before it is applied and gives it a suspicion score; the highest-scoring changes go to human auditors, who can review only a small fixed share. The reviewer is a small off-the-shelf model; it sees the diff and the ticket. At the moment it gives high scores to many correct but complex changes, which uses up much of the audit budget.

An engineer proposes a rule: every change must come with a rationale that explains each edited line in terms of the ticket and the behaviour of the systems it touches.

Would this rule help the review catch more sabotage within the same audit budget? Explain your reasoning, and say whether you would apply the rule to every change as proposed.
placeholder:: Your judgement of the rule
assessment-instructions:: Score out of 100. 50: (a) judging the rule by separation: the agent writes the rationales whether it is honest or sabotaging, so the rule helps only if it lowers suspicion on honest changes more than on sabotage (or raises it on sabotage), separating the two score distributions rather than shifting both; honest changes can be justified truthfully and coherently, while a sabotaging line often has no true justification that holds up, and a false or vague one often fails to make it look legitimate; and fewer false alarms on correct complex changes lower the audit threshold, which is set from honest changes, so more of the budget falls on sabotage (it may also narrow the spread of scores, which separates the distributions). 30 of the 50 for the core comparison of the effect on honest changes against the effect on sabotage; the rest for the reasons. 50: (b) where the rule separates: rationale lines grounded in the ticket or in the publicly documented behaviour of the standard tools can be checked by the reviewer, so a false or vague justification there often fails to make the sabotage look legitimate (it lowers suspicion on sabotage less than on honest changes), and the rule separates well there; claims about how the internal services behave cannot be checked by this reviewer beyond their consistency with the ticket and the diff, so a false one that fits them costs the attacker little and can lower suspicion on sabotage about as much as on honest work, so for changes whose justification rests on internal behaviour the rule separates little or even helps the attacker. Full credit for this distinction with its reason. Do not penalise an answer that notes a small reviewer can still be partly fooled, or swayed by the mere presence of an explanation, on checkable lines. Do not penalise an answer that notes the reviewer can still catch internal-behaviour claims that contradict the ticket or the diff. Credit the inference that a small off-the-shelf model knows public tools such as the web server and the database but not the lab's in-house services such as Kestrel. Within these 50, a sound refinement (restrict rationales to checkable claims, give the reviewer the internal documentation, send changes resting on uncheckable claims to stricter handling, apply the rule only where it separates) can make up for a thin account of either side. Points already credited in one element count once. Give credit for each point whenever the answer shows the idea, in any wording. Grade reasoning, not agreement: a learner who concludes the rule should not be adopted, or should be adopted only for some changes, can score fully if the reasoning above supports it. An answer arguing that some sabotage can be justified truthfully line by line (for example by exploiting an ambiguous ticket), so the rule separates less there, is a sound refinement and loses nothing. Cap at 45 if the answer never compares the rule's effect on honest changes with its effect on sabotage (for example it argues only that more information helps the reviewer, or only that the attacker can lie). Cap at 55 if it treats every rationale line as equally useful, never distinguishing what the reviewer can check from what it cannot. A pass is roughly 60. Model answer, for the feedback, not a grading checklist: "Probably yes, but not evenly. The agent writes the rationale whether it is honest or sabotaging, so the rule helps only if it helps honest changes more than sabotage. Honest changes have a true explanation, and giving it should stop the reviewer flagging so many correct complex changes; with fewer false alarms the audit threshold, set from honest changes, drops, and more of the budget lands on real sabotage. A sabotaging line usually has no true justification that holds up. Where the justification can be checked against the ticket or the documented behaviour of the web server or the database, which an off-the-shelf model knows, a false one is less likely to make it look legitimate and the sabotage stays more suspicious than honest work, so the rule separates well. Where it rests on how one of the lab's in-house services such as Kestrel behaves, a small off-the-shelf model has never seen it and cannot check it: a confident false rationale that fits the ticket costs little and may lower suspicion on sabotage as much as on honest work, so for those changes the rule separates little or even helps the attacker. I would keep the rule but treat lines justified only by internal behaviour as unverified, or give the reviewer the internal documentation."
feedback-instructions:: Name the strongest part of the answer in one sentence, then the single change that would most improve it. Ask at most one question, for the highest-value miss: if the learner judged the rule only by whether it gives the reviewer more information, ask who writes the rationale for a change that contains sabotage; if they treated every rationale line alike, ask which claims in a rationale this reviewer could actually check. If the learner asks about their score, explain plainly what earned and what lost points. At most five sentences.
