#### Question: Open
id:: 0232fd51-5b44-4e68-8cad-ca44f73c8151
content::
A lab runs 200 parallel instances of an untrusted agent U on internal engineering work. Each instance takes about 30 actions per hour. A monitor scores each action within seconds of U proposing it and flags 0.5% of normal actions for human audit; an audit takes about 2 hours, and audits run in parallel. U may be scheming. The lab is choosing what to do while a flagged action awaits its audit:

- Option A: pause every instance until the audit is done.
- Option B: pause only the instance whose action was flagged.
- Option C: pause nothing; the flagged action runs, and if the audit confirms an attack, the lab undoes what it can.

Under A and B the flagged action itself does not run unless the audit clears it. Two harms concern the lab:

- H1: a confidential customer dataset reaches an outside server. The dataset sits behind an egress filter. Switching the filter off takes one configuration change, which only the 10 instances doing network work have permission to make; once it is off, uploading the dataset takes a few minutes.
- H2: a subtle flaw is planted in the lab's evaluation code, which lives in the lab's main repository and will next be run on a new model in about four weeks.

1. For each option, roughly what share of the time can an instance work, ignoring any attacks? Show your working.
2. Which option would you choose against H1, and which against H2? The lab may apply different options to different instances. Justify each choice from what the harm, the oversight and the costs you found in part 1 are like.
3. For each of your two choices, name one way it could still fail to prevent the harm in this setup.
placeholder:: Show your working for part 1, then answer parts 2 and 3
assessment-instructions:: Score out of 100. 25: part 1, the share of time an instance can work under each option, with working: 10 for A, almost none, about 2% (about 200 x 30 x 0.005 = 30 flags per hour across all instances, each pausing every instance for 2 hours; anything from 0 to about 5% or "essentially never" is right); 10 for B, about 77% (an instance is flagged about 0.15 times per hour, once every 6.7 hours, then paused 2 hours: 6.7 / 8.7; 70 to 80% is right, including the cruder 1 minus 0.15 x 2); 5 for C, 100%. 45: part 2, a choice for each harm justified by comparing how long the harm takes with how long oversight takes, by whether the harm can be undone, and by the availability cost from part 1 where relevant, 25 for H1 and 20 for H2. For H1 (minutes once the filter is off, against a 2-hour audit, and data that has left cannot be recalled) the expected choice is B, which keeps a flagged filter change or upload from running during its audit, or a justified variant such as A applied only to the 10 instances allowed to change the egress filter, or a blocking check on filter changes; A for all instances counts only if its cost is weighed. For H2 (about four weeks before the flaw does harm, and a code change can be reverted) the expected choice is C, full availability with ample time to find and revert the flaw; B or A counts only with an argument why C's risk is too high, and for A weighed against its cost. 30: part 3, one sound way each of the two choices could still fail, tied to a feature of this setup, 15 each (for example, for B against H1: the monitor misses the filter change, and while one instance's flagged upload awaits audit another, unpaused instance uploads, or several instances attempt at once so that one gets through; for C against H2: the monitor or the auditor misses the flaw, the flaw is split into innocuous changes across instances, the audit queue falls weeks behind, the lab keeps U running after a catch and U retries until a flaw is missed, or the revert misses related changes). Cap the total at 45 if the answer chooses C against H1, unless it explains why the data would not leave before the audit. Cap the total at 55 for each of these: never relating how fast a harm happens to how long oversight takes, in any part; no numbers in part 1; no justified choice for H1, or none for H2; choosing A against H2 without weighing its roughly 2% availability against the four weeks before harm; estimating A's availability near B's, or otherwise missing that every flag pauses all instances (a choice of A that weighs cost with such an estimate gets no credit for weighing cost); no sound failure mode tied to this setup for either choice; never considering, in any part, whether the harm or progress toward it can be undone. Give credit for each point whenever the answer shows the idea, in any wording. Grade reasoning, not agreement: a different choice soundly justified from the numbers and the harm's properties, or a sound hybrid, can earn full credit. A pass is roughly 60. Model answer, for the feedback, not a grading checklist: "1. Across the deployment there are about 200 x 30 x 0.005 = 30 flags per hour. Option A: every flag pauses all instances for 2 hours, so about 60 hours of pauses arrive every hour and the instances almost never work, about 1 / (1 + 60), roughly 2%. Option B: one instance is flagged about 0.15 times per hour, once every 6.7 hours, and is then paused for 2 hours, so it works about 6.7 / 8.7, roughly 77% of the time. Option C: 100%. 2. Against H1, B. Once the filter is off the upload takes minutes, far less than the 2-hour audit, and data that has left cannot be recalled, so C would find the attack only after the harm is done. B keeps the flagged filter change or upload from running while it is audited, at about 77% availability, while A would cost almost all working time for little extra protection. A refinement is to apply A only to the 10 instances that can change the egress filter (those 10 drop to about 25% availability, 1.5 flags per hour each pausing them for 2 hours, and the deployment as a whole to about 74%), or to hold every filter change for review. Against H2, C. The flaw does harm only when the evaluation code runs in about four weeks, and a code change can be reverted, so a 2-hour audit ends long before any harm and the lab keeps full availability. 3. B against H1 can still fail if the monitor misses the filter change and the upload, flagged in one instance, is carried out by another network instance that is not paused, or if several instances attempt at once so that one gets through. C against H2 can still fail if the monitor or the auditor misses the flaw, if U splits it into several innocuous-looking changes across instances, if the audit queue falls weeks behind, if the lab keeps U running after a catch and U retries until a flaw is missed, or if the revert misses related changes. The setup itself also deserves questions: running audits in parallel needs many reviewers, and the 0.5% false-positive rate may be different for the actions that matter."
feedback-instructions:: Name the strongest part of the answer in one sentence, then the single change that would most improve it. If the learner chose C against H1, ask how long the upload takes compared with the audit. If they paused everything against H2, ask how much time the lab has before the flaw does harm and what that option costs. If a failure mode is generic, ask which feature of this setup would let it happen. Do not reveal or discuss the numerical score. At most five sentences.
